# DSH 启动 / 重启 / 关闭功能设计方案说明书

**版本：V2.0**
**适用对象：DeepSeek Harness Web 本地运行环境**
**设计目标：为 DSH 增加完整、稳定、低认知成本的启动、关闭、重启能力，并在 DSH 停止运行后仍提供独立的启动页面。**

---

## 1. 项目背景

当前 DeepSeek Harness Web 主要以持续运行状态为默认使用场景，缺少面向普通用户的完整生命周期控制能力。

现阶段主要存在以下问题：

1. 页面没有统一的「重启」和「关闭」入口。
2. 用户需要依赖命令行或外部脚本控制 DSH。
3. 直接在 DSH 自身进程内部执行关闭或重启存在"进程关闭后控制逻辑也同时消失"的问题。
4. DSH 关闭以后，原 Web 页面无法继续提供启动功能。
5. 重启过程中浏览器容易出现空白页、连接失败或需要手工刷新。
6. 原有技术实现中的进程检测、健康检查等概念不应直接暴露给普通用户。

因此，本方案增加一套独立于 DSH 主进程的轻量生命周期控制能力，并重新设计对应的前端交互。

---

# 2. 核心设计原则

整个功能遵循六项原则。

### 2.1 用户只理解三个动作

前台只出现：

* **启动**
* **重启**
* **关闭**

不向普通用户展示：

* 进程号
* Watchdog
* Supervisor
* Boot ID
* SIGTERM
* Health Check
* Port
* Restart Request

这些概念仅存在于内部实现和日志中。

---

### 2.2 风格接近 macOS 启动体验

视觉目标不是制作一个"服务器管理后台"，而是接近 Mac 开机、系统恢复、应用启动时的感觉：

* 大面积留白
* 中央视觉焦点
* 极少文字
* 柔和渐变
* 微弱光晕
* 简单状态变化
* 不显示大量技术参数
* 操作完成后自动进入下一状态

用户看到的是：

> DSH 已关闭 → 启动 DSH → 正在启动 → 自动打开

而不是一套复杂运维面板。

---

### 2.3 后台复杂，前台简单

后台可以有完整的：

* 状态检测
* 进程生命周期管理
* 超时控制
* 异常恢复
* 日志记录
* 实例识别
* 启动验证

但前端仅翻译为：

> 正在启动……

> 启动时间比平时稍长……

> 暂时没有启动成功。

---

### 2.4 DSH 关闭后，控制页面必须继续存在

生命周期关系必须设计为：

```text
DSH 控制服务
│
├── 启动 DSH
├── 关闭 DSH
├── 重启 DSH
├── 检查 DSH 是否可用
└── 提供关闭后的启动页面

DSH 主程序
└── 127.0.0.1:3080
```

不能让"启动 DSH"的能力依赖已经关闭的 DSH 自身。

---

### 2.5 尽可能自动恢复

正常情况下用户不应该负责：

* 手工刷新页面
* 再点"进入"
* 重新选择会话
* 重新选择工作区
* 判断程序有没有启动成功

系统自行完成。

---

### 2.6 不影响 DSH 原有界面

生命周期功能属于增强层。

不得大规模修改：

* 会话页面
* 工作区
* 模型选择
* 消息输入区
* Session Log
* DSH 原有布局

只在左侧底部增加控制入口。

---

# 3. 总体产品结构

最终形成两个用户界面。

## 页面 A：DSH 正常运行页面

沿用现有 DSH Web。

在左侧边栏底部、设置按钮上方加入：

```text
┌──────────────┬──────────────┐
│   ↻  重启     │    ⏻  关闭    │
└──────────────┴──────────────┘

⚙ 设置
```

---

## 页面 B：DSH 独立启动页面

DSH 关闭以后进入独立页面。

页面主要内容：

```text
                 DSH Logo

             DeepSeek Harness

                DSH 已关闭

        需要使用时，可以随时重新启动。


             ▶  启动 DSH


               查看日志
```

除此之外不提供复杂操作。

---

# 4. 页面 A：正常运行状态设计

## 4.1 插入位置

按钮位于当前左侧栏最下部。

顺序：

```text

      ↓
……
      ↓
[ 重启 ] [ 关闭 ]
      ↓
设置
      ↓
额度 / 状态
```

如果当前版本的额度胶囊位于页面右下角，则不改变。

# 5. 「重启」「关闭」按钮视觉设计

## 5.1 尺寸

建议：

* 总宽度：与左侧栏内容区域一致
* 高度：38 px
* 两按钮间距：8 px
* 单按钮宽度：约 50%
* 圆角：9 px
* 边框：1 px
* 字号：14 px
* 图标：16 px

---

## 5.2 默认状态

重启：

```text
↻  重启
```

关闭：

```text
⏻  关闭
```

均采用：

* 白色或透明浅底
* 浅灰描边
* 深灰文字
* 不使用强烈颜色

原因：

这两个功能属于低频管理操作，不应该和「新会话」「发送」争夺视觉注意力。

---

## 5.3 Hover

### 重启

背景略微变深。

图标轻微旋转约 15°～25°即可，不做持续动画。

### 关闭

Hover 时才出现轻微的暖红色：

```text
文字：#D94A4A
背景：极浅红
边框：浅红
```

避免默认情况下整个按钮呈红色。

# 6. 重启交互设计

## 6.1 点击重启

弹出确认卡片。

### 标题

**重启 DSH？**

### 说明

> 重启过程中页面会暂时无法使用，完成后会自动恢复。

次级说明：

> 当前会话和设置不会被删除。

### 按钮

```text
取消        立即重启
```

---

# 7. 重启接管界面

用户确认以后，**不跳转到关闭页面**。

当前页面直接进入全屏接管状态。

---

## 7.1 第一阶段

页面内容轻微淡出。

背景保持当前 DSH 页面轮廓，但：

```text
opacity: 0.2～0.3
blur: 6～10px
```

中央出现：

```text
          ↻

      正在重启 DSH

       请稍候……
```

下面可增加：

> 完成后将自动恢复页面。

---

## 7.2 动画风格

不使用传统服务器式进度条。

推荐采用类似 macOS 启动过程的：

* 柔和圆形呼吸动画
* Logo 微弱亮度变化
* 非明确百分比动画

原因是程序启动时间无法准确预测。

---

# 8. 重启后台流程

内部执行：

```text
用户点击重启
        ↓
浏览器进入接管状态
        ↓
记录当前页面
        ↓
发送重启请求
        ↓
关闭旧 DSH
        ↓
启动新 DSH
        ↓
等待 DSH 可以正常响应
        ↓
确认新实例已经真正启动
        ↓
恢复页面
```

---

# 9. 重要顺序

必须严格执行：

```text
① 显示重启接管 UI
② 等待浏览器完成一次绘制
③ 再发送重启请求
```

不能：

```text
发送重启请求
↓
再显示接管页面
```

否则 DSH 如果停止速度过快，会增加页面状态混乱风险。

---

# 10. 重启完成

新实例确认正常以后显示：

```text
         ✓

      DSH 已重新启动

      正在恢复……
```

约停留：

**500～1000 ms**

随后：

* 重新加载原页面；
* 或恢复原会话。

---

# 11. 原页面恢复

重启前记录：

```text
lastUrl
lastSessionId
lastWorkspace
scrollPosition（可选）
```

例如用户原来正在：

```text
/session/abc123
```

重启以后优先回：

```text
/session/abc123
```

而不是 DSH 首页。

---

# 12. 点击「关闭」

关闭和重启必须明确区分。

点击关闭以后出现确认卡片。

---

## 12.1 普通情况

标题：

**关闭 DSH？**

说明：

> 关闭后，DSH 将停止运行。

第二行：

> 需要使用时，可以随时重新启动。

操作：

```text
取消        关闭
```

关闭按钮此时使用红色。

---

# 13. 如果存在正在执行的任务

如果能够获取当前任务状态，则关闭时进一步判断。

若没有执行任务：

直接使用普通确认框。

若存在任务：

显示：

**关闭 DSH？**

> 当前还有任务正在运行。

> 关闭后，正在执行的任务将停止。

操作：

```text
取消        仍然关闭
```

不要求用户理解所谓：

* Graceful shutdown
* Force shutdown
* Safe Point

这些全部由后台负责。

---

# 14. 关闭流程

建议流程：

```text
点击关闭
   ↓
确认
   ↓
保存当前页面信息
   ↓
进入独立启动页面
   ↓
独立控制服务确认页面已加载
   ↓
停止 DSH
```

这里最关键的是：

## **先切换到独立页面，再真正关闭 DSH。**

---

# 15. 为什么必须这样设计

如果顺序是：

```text
关闭 DSH
↓
再跳转页面
```

浏览器可能先进入：

```text
ERR_CONNECTION_REFUSED
```

因此推荐：

```text
DSH 页面
↓
独立启动页面已经显示
↓
后台再停止 DSH
```

从用户视角来看，画面连续，不出现浏览器错误页面。

---

# 16. 独立启动页面设计定位

该页面是整个系统最重要的新界面。

设计关键词：

**安静、简洁、稳定、系统感。**

参考方向：

* macOS 登录前界面
* Mac 启动过程
* macOS Recovery 的简化视觉
* 苹果设备首次进入系统时的留白与中心构图

但不直接复制苹果品牌元素。

# 24. 启动状态设计

点击：

**启动 DSH**

以后：

1. 立即禁止重复点击；
2. 按钮淡出；
3. 页面进入启动状态。

## 24.1 正常启动状态

中央显示：

```text
           ◌

       正在启动 DSH

      通常只需要几秒钟
```

不要显示：

```text
PID
端口
进程名称
启动命令
```

# 25. 启动动画

建议采用：

### 方案 A：Logo 呼吸

Logo：

```text
opacity 0.7 → 1 → 0.7
```

循环约：

```text
1.8～2.2 秒
```

### 方案 B：Logo 下方小型加载环

非常细的圆形进度动画。

推荐 A，因为更接近系统启动体验。

# 26. 启动成功

显示：

```text
          ✓

       DSH 已启动

      正在为你打开……
```

停留：

```text
600～1000 ms
```

随后自动进入 DSH。

不增加：

```text
[进入 DSH]
```

这种无意义的额外点击。

---

# 27. 启动后回到哪里

如果存在之前记录：

```text

```

则：

```text
优先回到关闭前页面
```

否则：

```text
进入 DSH 首页
```

---

# 28. 启动时间稍长

例如 15 秒仍未完成。

页面不要变成错误页。

改为：

```text
正在启动 DSH

启动时间比平时稍长，请稍候……
```

可以提供：

```text
继续等待
```

以及：

```text
查看日志
```

# 29. 启动失败

例如 60～90 秒仍没有正常启动。

显示：

```text
            !

     DSH 暂时没有启动成功

          可以再试一次。


        [ 重新启动 ]

          查看日志
```

避免写：

```text
ERROR
FATAL
TIMEOUT
PORT ERROR
PROCESS EXITED
```

除非用户打开日志。

# 30. 日志页面

日志属于辅助排错界面，不需要大众化到完全隐藏技术内容。

点击：

**查看日志**

可以打开抽屉或独立窗口。

建议包含：

```text
22:01:32 已收到启动请求
22:01:33 正在启动 DSH
22:01:38 DSH 已启动
22:01:39 页面已恢复
```

默认是用户友好的事件日志。

增加：

```text
显示详细日志
```

以后才显示原始命令行输出。

# 31. 底层服务命名

不再使用：

**Watchdog**

作为任何用户可见名称。

代码内部建议也逐步统一命名。

推荐：

```text
dsh-controller
```

或：

```text
dsh-launcher
```

其中建议优先：

## `dsh-controller`

因为它实际负责：

* start
* stop
* restart
* status

而不只是启动。

---

# 32. 用户界面中不显示底层服务名字

即使内部叫：

```text
dsh-controller
```

页面也不需要写：

> DSH Controller 正在运行

用户只看到 DSH。

```http

```

# 36. GET /api/status

普通响应：

```json
{
  "state": "running"
}
```

状态仅需要：

```text
running
stopped
starting
stopping
restarting
error
```

---

# 37. POST /api/start

响应：

```json
{
  "ok": true
}
```

随后前端开始轮询状态。

---

# 38. POST /api/stop

响应：

```json
{
  "ok": true
}
```

真正停止工作由控制服务完成。

---

# 39. POST /api/restart

响应：

```json
{
  "ok": true
}
```

不需要把内部进程信息暴露给前端普通 UI。

---

# 40. 内部实例识别

虽然用户看不到，但后台仍建议保留实例 ID。

例如：

```json
{
  "instanceId": "1723645920-a8fe"
}
```

重启前：

```text
instance A
```

重启以后必须：

```text
instance B
```

才能判断：

**真正完成了一次重启。**

不能单纯因为：

```text
HTTP 200
```

就宣布成功。

---

# 41. 状态确认机制

建议启动成功必须满足：

```text
DSH HTTP 可访问
+
核心接口响应正常
+
新实例已经 ready
```

才能通知前端：

```text
running
```

---

# 42. 关闭方式

默认执行正常关闭。

流程：

```text
请求关闭
↓
通知 DSH 退出
↓
等待正常结束
↓
如果超过合理时间仍未退出
↓
执行兜底结束
```

用户不需要选择。

---

# 43. 防止重复操作

以下状态：

```text
starting
stopping
restarting
```

全部禁止再次执行：

```text
start
stop
restart
```

避免用户连续点击导致多个生命周期请求同时执行。

---

# 44. 控制锁

后台应存在统一生命周期锁：

```text
lifecycleLock
```

规则：

```text
任何时刻只允许一个生命周期动作执行
```

例如：

正在重启：

```text
restart
```

此时新的：

```text
stop
```

应该返回：

```text
busy
```

而不是并发执行。

# 45. 浏览器页面状态

建议内部前端状态机：

```text
RUNNING
    ↓
RESTART_CONFIRM
    ↓
RESTARTING
    ↓
RESTORING
    ↓
RUNNING
```

关闭：

```text
RUNNING
    ↓
STOP_CONFIRM
    ↓
SWITCH_TO_LAUNCHER
    ↓
STOPPED
```

启动：

```text
STOPPED
    ↓
STARTING
    ↓
READY
    ↓
RETURN_TO_DSH
```

---

# 46. 独立页面自身不能依赖 DSH

启动页面使用：

* 独立 HTML
* 独立 CSS
* 极少 JS

不能加载：

```text
3080/assets/*
```

否则 DSH 一关闭，启动页面资源也会丢失。

启动页所有核心静态资源应由：

```text
3081
```

自行提供。

---

# 47. 页面体积目标

启动页面应非常轻。

推荐：

```text
HTML + CSS + JS < 300 KB
```

非硬性限制。

不要引用大型前端框架作为必须条件。

如果当前实现允许，甚至可以使用：

```text
原生 HTML
CSS
JavaScript
```

构建。

这样启动速度和可靠性最高。

---

# 48. 本地安全设计

控制接口只监听：

```text
127.0.0.1
```

不要默认监听：

```text
0.0.0.0
```

避免局域网其他设备操作用户的 DSH。

---

# 49. API 请求安全

至少做到：

1. 仅允许 localhost。
2. 对 Origin / Host 做基础检查。
3. 生命周期请求使用 POST。
4. 防止普通网页跨站触发生命周期命令。
5. 不提供任意 shell 命令接口。
6. API 参数采用白名单。

---

# 50. Windows 自启动

控制服务应该随 Windows 登录自动运行。

因为：

如果 DSH 已关闭，但是控制服务也不存在：

```text
启动 DSH
```

就无法工作。

因此结构应为：

```text
Windows 登录
↓
DSH Control Service 自动启动
↓
根据配置决定 DSH 是否自动启动
```

---

# 51. 是否让 DSH 随系统自动启动

建议增加内部配置：

```text
autoStartDSH = true / false
```

但 V2 第一阶段可以不在 UI 展示。

默认行为根据现有 DSH 使用习惯决定。

---

# 52. 关闭 DSH 不等于关闭控制服务

用户点击：

**关闭 DSH**

实际关系：

```text
DSH        → 停止
控制服务    → 保持运行
启动页面    → 保持可用
```

这是整个架构的核心。

---

# 53. 控制服务什么时候退出

只有：

* 用户退出整个 DSH 控制环境；
* Windows 注销；
* Windows 关机；
* 或显式结束后台服务；

才退出。

普通：

```text
关闭 DSH
```

不退出。

# 73. 最终产品定位

这套功能不应被设计成：

> DSH 运维控制台

而应该被设计成：

> **DSH 自身的一套系统级启动体验。**

用户的认知模型应该非常简单：

```text
正在用
↓
重启

或

正在用
↓
关闭
↓
以后点击启动
↓
继续使用
```

整个功能的价值并不在于让用户看到更多系统信息，而是在于：

> **即便 DSH 自己停止运行，用户仍然始终有一个稳定、漂亮、明确的入口，可以重新把它启动起来。**

视觉上采用 macOS 式大面积留白、中央聚焦、极简文字和柔和状态过渡；技术上则由一个独立、长期存在的本地控制服务完成真正的生命周期管理。

这应作为 DSH 启动、关闭、重启功能的正式 V2 设计基线。
